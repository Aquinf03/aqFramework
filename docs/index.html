Getting started

Aquin is a developer environment and framework for building and checking models. The unit of work is a directory. You grow that folder, run aq against it, and keep enough on disk that you (or someone else) can fork, resume, and audit what happened. Disk is the source of truth. The UI is a view. The Unix is the product.

How the pieces fit

NameWhat it is
AquinThe product: developer environment and framework.
aqThe CLI you type (TypeScript). Quiet, cwd-based, like git.
KernelPython under aq/kernel/. Fit, eval, serve, hash. Talks to the CLI through files.
TrainA directory with instructions.md + recipe.yaml. The real unit of work.
AgentLives inside that Unix: same cwd, same files, same verbs. Not a side chat.

Flow is always the same shape: you work in a train folder, the CLI routes verbs, the kernel does the numeric work, artifacts land back on disk. Accounts and docs live at aq.aquin.app. Auth is identity and tokens only — it does not own trains. Sign in.

The directory system

A train is any folder with both instructions.md (what this is for) and recipe.yaml (the full train API for built-ins). aq init scaffolds the rest. Convention over registration: drop a file in the right slot and it exists. No central registry.

train folder 
my-train/
  instructions.md          REQUIRED - what this train is for
  recipe.yaml              REQUIRED - kernel spec (aq does not override)
  train.ts                 OPTIONAL - placeholder; aq does not read yet
 
  data/                    your datasets (path from recipe)
  evals/                   user probes (.csv / .jsonl) - no bundled zoo
  methods/                 optional train-local fit adapters (override kernel)
  tools/                   scripts: tools/<name>.{py,ts,js,sh}
  skills/                  agent skills (+ optional MCP)
  memory/                  agent memory markdown
  sandbox/                 scratch for agent / tools
  connections/             connection defs (slot)
  schedules/               yaml/json schedules
  stages/                  nested trains (each is itself a train)
  jobs/                    SYSTEM - process queue state
  artifacts/               SYSTEM - checkpoints, metrics, runs, chats, …

data/ and evals/ are yours. methods/, tools/, skills/, schedules/, and stages/ extend the train locally. jobs/ and artifacts/ are system-owned. Forking copies the science and skips runtime state so a variant starts clean. Full layout: Train folder.

CLI

aq is the face. Cwd is the workspace. Help is short. Verbs do one thing and compose: aq train fits, aq eval scores, aq serve generates, aq status / aq diff read history, aq job run files long work with resource asks, aq fork branches a train.

On a TTY, bare aq opens the agent. Without a TTY it prints help. Account tokens live under ~/.aquin; provider keys for the agent under ~/.aq. Reference: CLI.

Kernel (Python)

The kernel is the programmatic engine. TypeScript and Python do not share memory. They talk through files:

  1. CLI writes artifacts/request.json
  2. Spawns kernel/run.py on the train path
  3. Kernel runs the op (hash, train, eval, checkpoint, serve)
  4. Writes artifacts/result.json and appends metrics.jsonl; live steps stream on stderr

For built-ins you do not write Python. recipe.yaml is the API. Custom fits go in methods/<name>.py with fit(src, rec). See Recipe and Methods.

Agent

The agent is not a chat toy with a private filesystem. It is a resident of the train: same cwd, same recipe.yaml, same tools. Humans own the eval gate. Surfaces: interactive aq / aq agent, one-shot aq ask, resume via aq chat, workers via aq spawn. Details: Agent and Skills, tools & MCP.

What “working” means

A stranger should be able to open a train, point the recipe at their data, set their gate, run train then eval, fail, inspect, edit one file, fork, and run again. Long work files as aq job run. There is no preset eval zoo. You write the probes.
